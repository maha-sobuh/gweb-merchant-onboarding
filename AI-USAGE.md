# AI Usage Report

This document describes how AI tools were used to build the Merchant Onboarding & Underwriting Intake Layer, what the AI produced versus what I did myself, and which bugs and mistakes came up along the way.

## Summary

Most of the code in this repository was generated by AI assistants. I did not hand-edit the generated code. My role was to direct the work, review what was proposed, choose between options, run and interpret the tests, and commit the results in small slices. Where I say "I" below, that is the human side of the workflow; where I say "the assistant", that is the AI.

## Tools used

| Tool | How it was used |
|------|-----------------|
| Cursor | Early part of the project. I gave it prompts and it generated code in the editor. It hit its usage limit early on, so I stopped relying on it. |
| Claude (chat) | The rest of the project. Claude wrote the code, tests and documentation in the chat, and I copied it into the repository. |

The commit history preserves the order of work.

## Workflow

1. For each phase I wrote a detailed prompt: hard constraints, the exact file layout, the DynamoDB key design, endpoint behaviour, error handling, IAM scope, test requirements, and an explicit "do not build this yet" list. For fixes I sent short messages, usually with the failing output pasted in.
2. The assistant proposed code, sometimes with several options for a design question. I reviewed the options and picked the one that fit best.
3. I saved the files locally (Windows, PowerShell, Python 3.13) and ran `pytest` and `sam validate`.
4. I pasted the output back to the assistant. Failures were diagnosed from the real output rather than guessed.
5. Once green, I committed. The pattern is one commit for the code and a separate follow-up commit for its tests.

## How the output was verified

- Automated tests with moto, so there are no real AWS calls during the test run: all tests pass (full output in `docs/pytest-output.txt`).
- `sam validate` on `template.yaml`.
- After every file save, a check of the file size and an import or test run (see the empty-file issue below).
- The Docker/WSL2 setup on my machine did not work, so `sam local start-api` was never run. Behaviour is verified through the test suite and template validation, not through local API emulation.

## Bugs and problems found

### 1. DynamoDB rejects Python floats (hit three times)

DynamoDB's resource API does not accept `float`; it needs `Decimal`. This failed at runtime in several places (for example the applicant ownership percentage and the MCC confidence score). Fixing each place separately kept reintroducing the bug, so a shared helper, `to_dynamo_safe` in `src/common/dynamo_utils.py`, now recursively converts floats to `Decimal`, and the newer models use it (evaluation, submission).

### 2. Empty and BOM-corrupted files on save

Saving files through PowerShell here-strings sometimes produced 0-byte files, or files with a byte-order mark that broke JSON loading. The fix was procedural: save from the editor, and verify size and import before running tests.

### 3. `ApplicationStatus.SUBMITTED` did not exist

The submit code referenced `ApplicationStatus.SUBMITTED`, but the enum only contained `IN_PROGRESS`. The handler and service unit tests all passed because the handler tests use a fake repository, so the mismatch was invisible to them. The moto-backed repository tests, written afterwards, failed immediately with an `AttributeError`. Without them, every real `POST /applications/{id}/submit` would have returned a 500. The enum value was added and the repository tests were kept.

Lesson: tests that only use fakes can hide a contract mismatch between layers. The repository tests exercise the real conditional-write logic against moto.

### 4. Missing access patterns from the spec

While building the evaluation phase, the spec's list of required access patterns turned out to be only partly implemented. `list_persons` and `list_documents` (DynamoDB `Query` over the application partition) were added.

### 5. Timeout mismatch between the spec and API Gateway

The assessment spec allows 45 seconds, but an API Gateway REST API has a hard 29-second integration limit. The design uses a 28s Lambda timeout and a 20s internal `DeadlineGuard`. The reasoning is documented in the README.

### 6. Stale README

The original README still described only Phase 1 and mixed Python 3.12 and 3.13 statements. The Phase 1 prompt asked for Python 3.12, but the implementation runs on 3.13 to match the local environment. The README was rewritten to describe the final implementation consistently.

### 7. The AI timeout guard was cooperative

Writing the slow-dependency test showed that the adapter guard only checked the remaining time before a call. A genuinely hanging adapter would have blocked the request until Lambda's own timeout. A hard timeout (`_call_ai`: a worker thread plus `future.result(timeout=...)`) was added, and the test now proves the request returns before the deadline with a safe fallback.

### 8. Numbers returned as strings from submit

The end-to-end test showed submit returning numeric fields (for example the effective rate) as strings, because floats were converted to `Decimal` before the response was serialized. The conversion now happens only at the DynamoDB write.

### 9. Wrong status in the review snapshot

The demo transcript showed the snapshot reporting `IN_PROGRESS` while the application was `SUBMITTED`. Fixed, with the unit test updated.

### 10. GET returned metadata only

Reviewing the assessment against the code showed that `GET /applications/{id}` returned only the metadata, so a client could not resume or review an application. It now returns the full normalized state, the missing items and `readyToSubmit`.

### 11. Documentation claims checked against the code

While writing the security and MCC documentation, statements the assistant had made earlier were checked against the code and corrected. The upload checks are weaker than first described (see below), and the MCC catalog's provenance is not recorded even though a code comment names Visa and Mastercard as the source.

## Known weaknesses in the AI-generated work

These are documented in the README as well:

- The submit step is not atomic (status update and snapshot write are two calls); a single `transact_write_items` would fix it.
- Nested evaluation output uses `snake_case` keys while the rest of the API uses `camelCase`.
- There is no authentication.
- Document checksums are client-reported and not re-verified.
- Upload validation is partial: the 25 MB cap and the content type allowlist apply to the declared values at presign; on completion only the object's existence and actual size are read back from S3, and the size is not compared with the declared size. There is no file-signature check.
- There is no web UI.
- The MCC catalog is a 35-code subset created with AI assistance, with no scripted import and no recorded per-entry provenance.

## AI inside the product

The solution includes an AI evaluation boundary (`AIAdapter`), but the only implementation is `MockAIAdapter`. No LLM is called at runtime. There is no OCR: statement extraction returns an empty, low-confidence placeholder, and statement analysis works only when the client supplies values directly. The adapter's output is schema-validated, size-capped and timeout-guarded, and it fails safe. The numeric effective rate is computed deterministically and never comes from the model.

## Representative prompts

Each phase started from a structured prompt that fixed the scope and constraints up front. This is an abridged excerpt of the Phase 1 prompt:

```text
Build Phase 1 (Foundation) of a serverless Merchant Onboarding backend for AWS. This is the FIRST of several phases - build ONLY what's specified below, nothing more. Do not implement document upload, MCC classification, or AI evaluation yet - those come later.

## Hard Constraints (non-negotiable)
- Backend compute: AWS Lambda ONLY. No EC2, ECS, Fargate, or any always-on server.
- Language: Python 3.12
- Infrastructure as Code: AWS SAM (template.yaml)
- Data validation: Pydantic v2 (no FastAPI, no Mangum - plain Lambda handlers)
- Database: DynamoDB, single-table design
[...]
## DynamoDB table design
Single table named MerchantOnboarding.
- Partition Key: PK (String)
- Sort Key: SK (String)
[...]
## IAM / least privilege
- In template.yaml, each Lambda function's IAM policy must only grant the exact DynamoDB actions it needs [...]
[...]
After generating everything, give me a summary of every file you created and what each one does, so I can review it file-by-file before we move to Phase 2.
```

The full prompt also specified the project layout, the endpoints and their status codes, the error shape, the testing requirements, and a "what NOT to do" list. Asking for a file-by-file summary at the end of each phase was how I reviewed the output before moving on.

Later work used shorter, task-oriented messages, often with code or test output pasted in. Examples from the final stretch of the project, translated from Arabic:

- "We want to continue working on the project. Do you remember where we left off?" (resuming work across sessions)
- The Phase 5 handler, service, model and repository code pasted in, to get the tests written against it.
- The full `pytest` output pasted in after failures, to diagnose the `AttributeError` above.
- "Where exactly do I put the files you gave me?" (placement in the existing `tests/unit/` layout)
- The output of `Select-String` on the source files, to confirm whether an edit had actually been saved.
